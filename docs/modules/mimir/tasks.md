# Mímir Tasks — MVP Specification

> Status: working MVP specification. This document records the current agreed direction for Mímir Tasks and should guide domain, API, persistence, UI, and test design.

## Purpose

Tasks are the smallest first-class unit of actionable work in Mímir.

The MVP should make it fast to capture, assign, organize, break down, work, complete, reopen, and audit a task without forcing users to create a project first.

Mímir follows a **guided flexibility** rule: organizations may configure workflows, fields, permissions, templates, views, and SLA policy later, but core object semantics remain stable. A Task should not become an arbitrarily configurable replacement for Projects, Programs, Portfolios, Tickets, or Notes.

A key design principle is:

> When work outgrows its current structure, promote it instead of making the current object infinitely complex.

| P0 | Core content | Title and optional description |

| P0 | Priority | Low, Normal, High, Urgent; Normal by default |
| P0 | Assignment | Zero or one primary assignee |
| P0 | Dates | Optional due date |
| P0 | Audit trail | Immutable audit events for meaningful changes |
| P0 | Task collection | Basic search, sort, and filter |
| P1 | Child tasks | Limited nesting for lightweight decomposition |
| P1 | Project association | Optional Project context |
| P1 | Notes | Lightweight notes associated with work |
| P1 | Task -> Project | Promotion while preserving source identity and history |
| P1 | Time tracking | Manual entries and a basic timer |

The first implementation milestone is **Mímir Tasks — Foundation**:

> Capture -> assign -> organize -> break down -> work -> complete -> inspect history.

## Identity

Tasks have two distinct identifiers.

### System identity

`Id` is a **UUIDv7** generated by the application/system.

Rules:

- globally unique
- immutable for the lifetime of the Task
- used by persistence relationships and public API/resource identity
- safe across exports, restores, migrations, self-hosted deployments, and future distributed processing
- must not rely on a database auto-increment value for entity identity

UUIDv7 is preferred over random UUIDv4 because it retains useful time-ordering characteristics and is generally friendlier to database indexes.

### Human-readable key

Each Task also receives a human-readable key such as:

`TASK-184`

The key is composed from:

- an entity-type prefix, default `TASK`
- a tenant-scoped sequence number

Future tenant configuration may allow custom prefixes, for example `ENG-184` or `OPS-184`.

Rules:

- a human-readable key is an immutable alias once assigned
- sequence numbers are not the system identity
- API contracts and foreign-key relationships must not depend on the human sequence number
- prefix changes affect newly created records only; existing keys do not change
- keys must remain searchable and resolvable after promotion or archival

### Promotion identity

Promotion from Task to Project creates a **new Project identity** rather than mutating the Task key.

Example:

```text
TASK-184
UUIDv7: 0199...
        |
        | promoted to
        v
PRJ-42
UUIDv7: 019a...
```

The original Task remains auditable and searchable. It records an explicit relationship to the resulting Project, and the Project records its source Task.

Do not rename `TASK-184` to `PRJ-184`. Human-facing identifiers may already exist in notes, audit events, exports, integrations, URLs, emails, or user memory.

## Core Task Record

The initial Task record should remain small.

| Field | Type | Required | Default | Mutable | Rule |
| --- | --- | --- | --- | --- | --- |
| `Id` | UUIDv7 | Yes | System | No | Immutable system identity |
| `Number` | Integer/sequence | Yes | System | No | Tenant-scoped human sequence |
| `Title` | String | Yes | — | Yes | Short summary of actionable work |
| `Description` | Text | No | null | Yes | Longer current definition/context |
| `Status` | TaskStatus | Yes | ToDo | Yes | Constrained MVP lifecycle |
| `Priority` | TaskPriority | Yes | Normal | Yes | Low, Normal, High, Urgent |
| `AssigneeId` | Actor/User ID | No | null | Yes | At most one primary assignee in MVP |
| `DueDate` | Date | No | null | Yes | Date only initially; no time-of-day requirement |
| `ParentTaskId` | UUIDv7 | No | null | Yes* | Subject to hierarchy invariants |
| `ProjectId` | UUIDv7 | No | null | Yes | Optional Project context |
| `CompletedAt` | Timestamp | No | null | System | Set on completion; cleared on reopen |
| `CreatedAt` | Timestamp | Yes | System | No | Immutable |
| `CreatedBy` | Actor ID | Yes | System | No | Immutable |
| `UpdatedAt` | Timestamp | Yes | System | System | Last meaningful persisted change |
| `UpdatedBy` | Actor ID | Yes | System | System | Actor responsible for last meaningful change |

The display key (for example `TASK-184`) may be derived from configured prefix plus `Number`; it does not need to be duplicated as mutable state if derivation remains stable.

## Associated Records

Keep related history and collections outside the Task row/entity rather than creating a single oversized Task record.

Expected associated concepts include:

- `TaskNote`
- `TaskTimeEntry`
- `TaskAuditEvent`
- `TaskTicketLink`
- child Tasks via `ParentTaskId`
- later: attachments
- later: dependency relationships
- later: custom field values

## Creation

Task creation should be intentionally lightweight.

The only user-entered required field for quick creation is:

- Title

On creation the system supplies:

- UUIDv7 `Id`
- tenant-scoped `Number`
- Status = To Do
- Priority = Normal
- CreatedAt / CreatedBy
- UpdatedAt / UpdatedBy

Description, assignment, due date, Project, parent Task, tags, and other metadata are optional.

A quick-create experience should allow entering a title and submitting without navigating through a large form.

## Status Lifecycle

MVP statuses:

- **To Do**
- **In Progress**
- **Done**
- **Cancelled**

`Blocked` is intentionally not an MVP status. Blocking is better treated as a condition or dependency concept if real usage proves it necessary.

Allowed MVP transitions:

| From | To |
| --- | --- |
| To Do | In Progress |
| To Do | Done |
| To Do | Cancelled |
| In Progress | To Do |
| In Progress | Done |
| In Progress | Cancelled |
| Done | In Progress |
| Done | To Do |
| Cancelled | To Do |
| Cancelled | In Progress |

Done and Cancelled are terminal for normal workflow presentation but are not permanently locked. Work in real organizations may need to be reopened or restored. Every such change is audited.

### Completion

When entering Done:

- set `CompletedAt`
- emit an audit event
- remove the Task from active/overdue calculations where appropriate

When leaving Done:

- clear the current `CompletedAt`
- preserve prior completion/reopen history in the audit trail
- emit a reopen/reset audit event

A parent Task may be completed while child Tasks remain open, but the UI must warn the actor and require an explicit confirmation.

## Priority

MVP priority values:

1. Low
2. Normal
3. High
4. Urgent

Normal is the default.

Priority describes importance. It does not define hierarchy, lifecycle, scheduling, or object type.

## Assignment

MVP supports zero or one primary assignee.

Rules:

- an unassigned Task is valid
- a single owner avoids ambiguity over responsibility
- watchers/followers/mentions may be added later without changing primary ownership semantics
- assignment changes are audited

## Due Date

Due date is optional.

Initial rules:

- no due date means the Task cannot be overdue
- an active Task with a due date before the current date is overdue
- Done and Cancelled Tasks do not present active overdue warnings
- reopening an overdue Task restores its overdue condition
- use a date-only value for MVP unless real use cases justify exact due times

## Child Tasks

A Task may contain child Tasks so users can decompose work without prematurely creating a Project.

Rules:

- a child is a normal Task with its own identity, status, assignee, priority, due date, history, and optional notes/time
- a newly created child inherits Project context from its parent when applicable
- inherited context may be changed when allowed by permissions/business rules
- a Task cannot be its own parent
- parent relationships may not form cycles
- nesting is intentionally limited

For MVP, support:

```text
Parent Task
└── Child Task
    └── Grandchild Task
```

That is a maximum of two descendant levels below the root Task.

If deeper structure is required, Mímir should suggest promotion to a Project rather than allowing arbitrary nesting.

Hierarchy describes scope/decomposition, not importance.

## Cancellation

Cancelled means the work is intentionally no longer being pursued.

Cancellation does not delete the Task.

A cancellation reason may be recorded but is not required for initial MVP. Candidate reasons include:

- no longer needed
- duplicate
- superseded
- other/free text

Cancelled Tasks:

- remain searchable
- retain UUID and human key
- retain audit/history
- may be restored/reopened
- are excluded from normal active work presentation

## Delete and Archive

Prefer preserving history over destructive deletion.

For MVP, normal user workflows should use Cancel and Archive rather than permanent deletion.

Permanent deletion, if implemented at all, should be limited to cases such as accidental newly-created records with no meaningful history, time, or relationships, and require appropriate authorization.

A core Mímir rule is:

> Never destroy work history merely to make the current state simpler.

## Editing and Audit Behavior

`UpdatedAt` and `UpdatedBy` represent the last meaningful persisted modification.

Meaningful changes should also emit audit events. Examples include:

- title changed
- status changed
- priority changed
- assignee changed
- due date changed
- parent Task changed
- Project association changed
- cancellation/restoration
- completion/reopening
- promotion to Project

Do not create audit noise for every keystroke while a user is editing. One logical save should produce one logical modification/audit result where practical.

CreatedAt and CreatedBy are immutable.

## Task -> Project Promotion

A Task may outgrow lightweight task structure and be promoted into a Project.

Promotion is an explicit domain operation.

The operation must preserve:

- source Task UUID and human key
- source Task history
- title and description/context
- relevant owner/assignment information
- relevant dates
- child Tasks
- Notes
- Time Entries
- Ticket relationships
- audit history and promotion event

The resulting Project receives its own:

- UUIDv7
- Project sequence number
- Project human key, such as `PRJ-42`

The Task records a relationship such as `PromotedToProjectId`, and the Project records its origin Task where appropriate.

The source Task should clearly resolve/display:

> TASK-184 was promoted to PRJ-42.

Promotion should not introduce a normal user-visible `Promoted` Task workflow status unless future behavior demonstrates a concrete need. Promotion is structural metadata and an audited event.

## Notes

Notes are lightweight contextual information associated with work.

For Mímir overall:

- Notes are personal by default
- Notes may be shared
- Notes may attach to Tasks, Projects, Tickets, and higher work contexts
- checklist items in Notes may later be promoted to Tasks

Within the Task MVP, distinguish:

- **Description** — editable current definition/context of the Task
- **Notes** — contextual information accumulated over time

Full knowledge/document management remains outside the Task concept.

## Time Tracking

Time tracking belongs to Mímir because time is recorded against work.

Task MVP should eventually support:

- manual time entry
- basic start/stop timer
- actor
- timestamp/start/end or duration
- optional description/note

Billing, cost accounting, and advanced resource planning are outside the initial Task MVP.

## Tickets

Tickets may exist independently of Projects.

A Ticket may:

- link to multiple Tasks
- create multiple Tasks
- retain its own lifecycle semantics

Tasks and Tickets remain separate domain concepts rather than being collapsed into a single generic issue type.

## Dependencies / Blocking

Formal dependencies are not required for the first MVP.

If early dogfooding demonstrates a clear need before a dependency model is justified, a simple blocked condition may be introduced:

- `IsBlocked`
- optional blocked reason

Do not build an advanced dependency graph until demonstrated usage requires it.

## Business Invariants

The Task domain must enforce at least these invariants:

1. `Id` is UUIDv7 and immutable.
2. Human-readable keys are immutable after creation.
3. Database auto-increment values are never the canonical entity identity.
4. CreatedAt and CreatedBy never change.
5. Status and Priority use constrained MVP values.
6. A Task may have at most one primary assignee in MVP.
7. A Task cannot be its own parent or ancestor.
8. Child nesting cannot exceed the configured MVP maximum.
9. Done and Cancelled Tasks may be reopened/restored through explicit audited transitions.
10. Task -> Project promotion creates a new Project identity and preserves the original Task.
11. Promotion, completion, reopening, cancellation, and meaningful ownership/context changes are auditable.
12. History is preserved by default; destructive deletion is exceptional.
13. Core object semantics are not tenant-configurable.

## Explicit MVP Exclusions

The initial Task MVP does not require:

- arbitrary/custom status workflows
- custom fields
- recurring Tasks
- advanced dependency graphs
- Gantt scheduling
- resource planning
- budget/cost accounting
- complex approval chains
- arbitrary relationship types
- multiple primary assignees
- AI-generated workflow behavior

These may be reconsidered after the core Task workflow has been dogfooded.

## Related Mímir Hierarchy

Tasks are part of a constrained work hierarchy:

```text
Portfolio
└── Program
    └── Project
        ├── Sub-project
        └── Task
            └── Child Task
```

Additional rules:

- Sub-project is a Project with a parent Project, not a separate entity type.
- Programs coordinate multiple Projects toward an outcome and do not directly own execution Tasks.
- Portfolios group/prioritize Programs and Projects and do not directly own Tasks or Tickets.
- hierarchy describes scope, not importance
- users are not required to use Program or Portfolio levels

The broader hierarchy and Project/Program/Portfolio specifications will be documented separately.
